topic: Web platform for sharing coffee bean reviews and brewing recipes (BeansJourney)
updated: 2026-07-31T13:43
---

- (decision) Why: user wants to buy coffee beans but has no way to know if a given bean is good before buying, and after buying doesn't know the best recipe/method for that bean; BeansJourney lets users share bean reviews and brewing recipes so others can research a bean before buying and find a good method after
- (capability) CAP-1 intent: system stores Roastery entities (name, contact/social media, location) each of which can hold many Beans, so users can see provenance for a bean; success: a roastery page lists its contact/social/location and every bean it produces
- (capability) CAP-2 intent: users can browse a Beans list and open a Bean detail page showing Process, Origin, Variety, Flavour Perception/Tasting Notes, Roast Date, Roast Profile, Purpose, Purchased On, Altitude; success: every field is visible on the bean detail page for any bean in the catalog
- (capability) CAP-3 intent: registered users can post a free-text Review on a bean as a thread (reddit-style), and other users can comment on and upvote reviews and comments; success: a bean page shows reviews sorted with visible upvote counts and nested comments
- (capability) CAP-4 intent: registered users can post a Recipe on a bean specifying brew method (americano, espresso, v60, french press, aeropress, tubruk, etc.), tools used (machine, grinder, dripper, etc.), and free-text process, and other users can comment on and upvote recipes and comments; success: a bean page shows recipes sorted with visible upvote counts, structured method/tools fields, and nested comments
- (capability) CAP-5 intent: users can register and log in via email, with the account requiring email verification before it is fully active; success: an unverified account cannot create beans/reviews/recipes/comments, and verifying the emailed link activates it
- (capability) CAP-6 intent: users can reset a forgotten password via a verification link emailed to them; success: submitting the emailed link lets the user set a new password and log in with it
- (capability) CAP-7 intent: logged-in users can edit their own profile (e.g. display name); success: a profile change persists and is reflected across the user's reviews/recipes/comments
- (capability) CAP-8 intent: admins can monitor and manage all platform resources through an admin console (basic analytics, beans, beans reviews, user activity history logs, user management); success: an admin can view analytics and perform CRUD/moderation on beans, reviews, and users, and view a user's history log, from the admin console
- (constraint) Backend is Laravel 13
- (constraint) Client-facing area (beans list/detail, reviews, recipes, auth) is built with React via Inertia.js
- (constraint) Admin console is built with Filament
- (constraint) Only registered, logged-in users may create beans, reviews, recipes, or comments; unauthenticated visitors are read-only
- (note) Non-goals not stated by user; drafted from context as assumptions pending confirmation
- (assumption) Assumed non-goal: no in-platform e-commerce/checkout for buying beans directly (site is review/recipe sharing, not a marketplace) -- not directly confirmed
- (assumption) Assumed non-goal: no native mobile app for MVP; web only via the Laravel/Inertia client -- not directly confirmed
- (assumption) Assumed non-goal: no real-time chat/messaging between users for MVP (interaction is via threaded comments only) -- not directly confirmed
- (note) Success signal not explicitly stated by user; drafted from Why + capabilities, pending confirmation
- (decision) Draft success signal: a user can look up a bean, read reviews and recipes with comments/upvotes to decide whether to buy and how to brew it, and can register (with email verification), post their own review/recipe, and see it appear immediately; an admin can view and moderate all of the above from the Filament console
- (question) User asked directly: for threaded reviews/recipes with comments and upvotes, is a relational DB (implied by Laravel/Eloquent) sufficient, or is NoSQL needed? Flagged as an architecture (HOW) decision for bmad-architecture rather than resolved in the spec -- relational (adjacency-list or nested-set comment tree) is a common, well-supported pattern for this shape at MVP scale
